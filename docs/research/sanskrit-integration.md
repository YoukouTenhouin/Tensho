# Sanskrit integration validation

Research date: 2026-10-04 UTC. Decision question: [issue #11](https://github.com/YoukouTenhouin/Tensho/issues/11), following [#3](https://github.com/YoukouTenhouin/Tensho/issues/3) and [#8](https://github.com/YoukouTenhouin/Tensho/issues/8). Architecture remains in [#9](https://github.com/YoukouTenhouin/Tensho/issues/9) and ADRs 0001–0009.

## Recommendation

**Unresolved blocker: neither pairing is verified for the agreed integrated Sanskrit experience.** Keep Latin delivery independent. Heritage's public form converts Devanāgarī and IAST in browser JavaScript before sending ASCII to its CGI; direct requests using the advertised form notation codes fail. Its automated-access protection also intervened in actual Edge requests. `sanskrit_parser` is the more promising hosted analyzer alternative: actual Edge requests returned usable JSON, and direct probes covered isolated morphology, competing passage segmentations and constituent analysis. Cologne returned substantial MW data to the HTTP probe, but all tested Edge dictionary operations failed. Exact dictionary article boundaries and identity mapping remain unresolved. Evidence is below; this is not an implementation or publication approval.

Do not relax passage analysis, silently introduce selected-text transliteration, automatically map same-spelling homographs, or describe an isolated-word-only adapter as completion of the Sanskrit scope. These constraints follow [ADR 0003](../adr/0003-sanskrit-input-capabilities-and-display-transliteration.md), [ADR 0004](../adr/0004-explicit-sanskrit-passage-segmentation.md) and [ADR 0005](../adr/0005-preserve-uncertainty-in-dictionary-mapping.md).

## Evidence and reproduction

[Exact requests](issue-11-probes/requests.json) and [bounded HTTP results](issue-11-probes/provider-results.json) record URLs, statuses, hashes, byte counts, durations and parsed analyzer responses. Observations used Python `urllib.request.urlopen(url, timeout=30)` with no account, credentials, API key, cookie jar, challenge solver or altered user agent. Dates in those files are batch-completion timestamps, not individual request timestamps. Dictionary evidence preserves record metadata rather than redistributing whole articles. Reproduce a **single** selected URL with `curl --get 'URL'`; URL query/path data is UTF-8 percent-encoded. Do not replay the list in bulk: HTTP 429 was observed, and Heritage crawler restrictions were discovered afterward; leave denied/protected paths alone unless permitted access has been established. These are read-only GET operations; content and availability can change.

[Edge harness](issue-11-probes/edge_probe.py), [first Edge results](issue-11-probes/edge-results.json), and [dictionary Edge results](issue-11-probes/edge-dictionary-results.json) distinguish actual browser extension fetches from Python HTTP observations and documentation. The temporary Manifest V3 extension used `credentials: 'omit'`, explicit host permissions, and a permission guard. No production extension workflow, source-page selection UI, safe article renderer, or complete end-to-end lookup was implemented by this research.

Reading samples come from the [Sanskrit Wikipedia article](https://sa.wikipedia.org/wiki/संस्कृतम्) (`संस्कृतम्`) and [Wikisource Bhagavadgītā chapter 1](https://sa.wikisource.org/wiki/भगवद्गीता/अर्जुनविषादयोगः) (`धर्मक्षेत्रे`, `मामकाः पाण्डवाश्चैव`, `सेनयोः`, `उवाच`). The pages were readable through the web research tool; ordinary Python requests received a Wikimedia user-agent policy response. The artificial unknown `झ्झ्झ्झ्झ`, emoji input and decomposed IAST are diagnostic controls, not quotations from those pages.

## Sanskrit Heritage: operation contract and native notation blocker

The live [Reader form](https://sanskrit.inria.fr/DICO/reader.html) identifies version 3.84 (2026-09-30). Its GET parameters are `text`, `t`, `lex=SH|MW`, `st=t|f` (sentence/word), `us=t|f` (unsandhied/sandhied), `font=roma|deva`, `topic` and `mode`. `mode=t` requests tagged alternatives from `/cgi-bin/SKT/sktreader.cgi`. The form's [own JavaScript](https://sanskrit.inria.fr/DICO/utf82VH.js) switches All mode to `sktgraph.cgi` and First/Best modes to `sktgraph2.cgi`. These are HTML user interfaces, not a versioned JSON contract. Operation parameters must follow the actual form, not names invented from general documentation.

The form lists `VH` (Velthuis), `WX`, `KH`, `SL` (SLP1), `DN` (Devanāgarī), and `RN` (IAST). Crucially, `convertByTrans` converts DN/RN text to Velthuis and changes `t` to `VH` **before submission**. Direct Reader calls with `t=DN&text=धर्मक्षेत्रे` and `t=RN&text=dharmakṣetre` returned HTTP 200 HTML containing `Fatal error` / `Unknown transliteration scheme`. The equivalent native `t=VH&text=dharmak.setre` returned three tagged solutions. Thus native CGI Devanāgarī/IAST support is **disproved for these tested codes**, despite the web UI supporting their entry. Do not copy its converter into the extension to evade the accepted input constraint. Other undocumented native mechanisms were not established. [Form conversion source](https://sanskrit.inria.fr/DICO/utf82VH.js), [observed cases h_deva/h_iast/h_ascii](issue-11-probes/provider-results.json).

The successful ASCII response retained a compound-initial `dharma` and `kṣetra` interpretations including nominative, accusative, locative and vocative readings; the three solutions had linked Heritage lemmas. It exposed both IAST and Devanāgarī text and used nested tables, character entities and links. Extraction must preserve solution boundaries, candidate boundaries and every supplied alternative; inner text alone loses relationships. This one result does not validate a general HTML extractor or universal morphology coverage. [Probe h_ascii](issue-11-probes/provider-results.json).

The separate [atomic-form lemmatizer](https://sanskrit.inria.fr/DICO/index.html#stemmer) submits GET `/cgi-bin/SKT/sktlemmatizer.cgi` with a selected category `c`: `Noun`, `Pron`, `Verb`, `Part`, `Inde`, `Absya`, `Abstvaa`, `Voca`, `Iic`, `Ifc`, `Iiv`, or `Piic`. Its form also calls the input converter. Calling only its default noun category cannot establish isolated analysis across grammatical categories. The [provider homepage](https://sanskrit.inria.fr/) explicitly directs prefixed verb analysis to the Reader. The atomic endpoint was inspected through its form, not operationally validated in every category.

The [manual](https://sanskrit.inria.fr/manual.html) describes ambiguity, compound components, vocative restrictions, punctuation and verse entry, and a 100-candidate threshold for access to some parsers. That is **not** a maximum input length or a guarantee of complete segmentation. The [linguistic resource page](https://sanskrit.inria.fr/xml.html) states classical-Sanskrit scope and omitted verbal categories for its downloadable banks. Do not equate those bank limitations with a measured completeness guarantee for the currently deployed Reader. No dependable hosted passage-length limit, request quota, latency guarantee or sanctioned extension API was established.

Actual Edge received HTTP 200 **Anubis protection HTML**, not analysis, with host permission. The web research tool also encountered protection, while Python sometimes retrieved ordinary pages and the ASCII analysis. The later [robots.txt](https://sanskrit.inria.fr/robots.txt) explicitly disallowed named AI crawlers including ChatGPT-User/GPTBot; Heritage probing stopped after that discovery. Successful earlier HTTP retrieval is not evidence of permission for automated production access. No challenge was bypassed. CORS was not established as a usable public interface, and the browser result independently blocks readiness. [Edge evidence](issue-11-probes/edge-results.json), [robots_h evidence](issue-11-probes/provider-results.json).

## sanskrit_parser: usable hosted alternative with limits

The [live Swagger contract](https://sanskrit-parser.appspot.com/sanskrit_parser/v1/swagger.json) advertises accountless GET routes under `https://sanskrit-parser.appspot.com/sanskrit_parser/v1`: `/tags/{p}`, `/splits/{v}`, `/presegmented/{v}`, `/parse-presegmented/{v}`, `/version/`. Only tags/splits were exercised here. Encode the whole input as one URL path component; these routes are not POST bodies or a query named `text`.

The [REST source](https://raw.githubusercontent.com/kmadathil/sanskrit_parser/master/sanskrit_parser/rest_api/api_v1.py) and [string implementation](https://raw.githubusercontent.com/kmadathil/sanskrit_parser/master/sanskrit_parser/base/sanskrit_base.py) explain the observed contract:

- Tags return `{input, devanagari, tags: [[lemma, [grammaticalTag, ...]], ...]}`. Empty results are `tags: []`. Preserve each supplied tuple; do not merge same-spelling tuples into an invented durable lexeme ID.
- Splits return `{input, devanagari, splits: [[constituent, ...], ...]}`. They contain no morphological tag objects; selecting a constituent requires a separate tags call. A literal returned `पाण्डवास्` was accepted by tags and produced five interpretations with lemma `पाण्डव`.
- The source uses encoding auto-detection, not a documented HTTP encoding selector. The splits route accepts `?strict=false`; the default is strict. Its call `find_all_paths(10)` imposes ten paths, without a total-count or truncation flag. Its internal final-s/final-r forms should be retained rather than silently replaced by displayed visarga.

These source statements describe retrieved source, not a verified deployed commit. The live responses below corroborate these particular shapes and limits. Neither source nor Swagger established a maximum supported passage length, fair-use quota or deployment SLA.

| Input and purpose | Observed tags | Observed splits / implication |
| --- | --- | --- |
| `संस्कृतम्`, Wikipedia title | 3 interpretations of `संस्कृत` | One whole-word path |
| `धर्मक्षेत्रे`, inflected compound | 5 interpretations of `धर्मक्षेत्र`, including locative singular and dual/vocative readings | 10 paths, including whole word and `धर्म` + `क्षेत्रे`; possibly truncated |
| `सेनयोः`, ambiguity | 12 tuples across `सेना` and `सेन` | 10 competing paths; provider echo becomes `सेनयोस्` in tags |
| `मामकाः पाण्डवाश्चैव`, joined passage | Empty tags (not an isolated form) | 10 paths; first `मामकास्`, `पाण्डवास्`, `च`, `एव` |
| `उवाच`, finite verb | 2 interpretations of `वच्` | Tag set retains first/third-person alternatives in Sanskrit terminology |
| `झ्झ्झ्झ्झ`, artificial unknown | Empty | Empty: valid observed no-match on supported notation |
| `धर्मक्षेत्रे कुरुक्षेत्रे ।` | Empty | Empty; removing only final danda produced 10 paths |
| `dharmakṣetre`, NFC IAST | Same 5 interpretation set as Devanāgarī | Same 10 paths |
| `dharmaks` + U+0323 + `etre`, NFD equivalent | Empty; echo contained misplaced script/combining mark | Empty: normalization limitation |
| `dharmakSetre`, ASCII test | Same 5 interpretation set | Same 10 paths; does not establish all ASCII schemes |
| `hello🙂`, unsupported-content control | Empty, with partly transliterated echo | Empty: service does not distinguish unsupported notation |

Every row is backed by the [recorded JSON responses](issue-11-probes/provider-results.json). These are provider interpretations, not independent linguistic judgments. Tags are Sanskrit labels: English UI normalization requires a complete explicit tag mapping, preserving unknown tags instead of dropping them. In Sanskrit grammatical convention `प्रथमपुरुषः` is third person and `उत्तमपुरुषः` first person; do not translate label names mechanically. Full label coverage was not validated.

A response with ten paths must be presented as **possibly truncated**; this probe did not recover an eleventh path to prove truncation for a particular input. Compounds and passage ambiguities remain visible; the [project README](https://github.com/kmadathil/sanskrit_parser) warns of both over-generation and missing valid forms. Punctuation cannot be silently stripped while claiming the original selected passage was analyzed. A future adapter needs an explicit punctuation/Unicode capability policy, with original text retained; NFC normalization was not applied to the selection by this research.

The browser extension successfully fetched both tags and splits with host permissions; raw fetch also succeeded without them, demonstrating why an application permission guard is necessary even when CORS allows a request. The tested guard made zero requests after revocation or when permission had never been granted. This verifies network access, not a full source-page reading workflow. [Actual Edge evidence](issue-11-probes/edge-results.json).

## Cologne MW: records are available, article resolution remains unverified

Use the actual native development surface `https://www.sanskrit-lexicon.uni-koeln.de/scans/awork/apidev/`, rather than assuming roadmap Salt or clean-URL endpoints are deployed. The [provider API guide](https://sanskrit-lexicon.github.io/csl-guides/developers/api) distinguishes those statuses. GET `getword.php?dict=mw&key=...&input=...&output=...` returned HTML for successful Python requests. GET `getword_xml.php` with the same parameters returned JSON containing `dict,input,output,key,accent,xml,html,status`; it is documented as **alpha**.

Live `input=deva&key=धर्मक्षेत्र` and `input=roman&key=dharmakṣetra` both resolved to canonical response key `Darmakzetra` and the same three MW record IDs `99972`, `99973`, `99974`. `input=slp1&key=agni` also worked. Use exact scheme name `roman` for the observed IAST input; the guessed `input=iast` gave HTML 403 or an XML 404 response after being echoed as `slp1`. A general guide's IAST output example does not validate that input alias. Output `roman` returned IAST article text, while an initial `output=deva` HTML request returned Devanāgarī. [Dictionary probes](issue-11-probes/provider-results.json).

The returned XML is not merely short meanings: it contains article bodies, references, headword fields, page/column metadata and `<L>` record identifiers, accompanied by rendered HTML strings. However, **one XML record is not necessarily one full dictionary entry or one homograph**. For `mA`, the successful XML response contained 23 records: initial inherited `H1B` records `153882`–`153889`; explicitly numbered head records `161686` (homograph 1), `161693` (2), `161697` (3), `161698` (4); and `H1A`/`H1E` continuation records including decimal IDs. `धर्मक्षेत्र` similarly returned an `H3` and two `H3B` records. An adapter returning the first record alone would truncate provider material. [Observed record metadata](issue-11-probes/provider-results.json), [CDSL API guide](https://sanskrit-lexicon.github.io/csl-guides/developers/api).

Preserve decimal IDs as strings, headword, supplied homograph markers, hierarchy/continuation information and original record order. Do not label every continuation a separate dictionary alternative or merge every same-spelling record indiscriminately. This investigation retrieved substantial entry content but **did not validate complete article grouping, selected-article retrieval by identity, safe rendering, or correspondence to the source scan**. The attempted `lnum=161686` follow-up was rate-limited, so it establishes no selection contract. A production resolver must be separately validated before claiming full MW entries.

There is no verified cross-provider lexeme-ID mapping. For `मा`, the analyzer supplied candidates including `मा#२`, `मा`, and `अस्मद्`; Cologne's own numbered homographs are a different identity namespace. **Never map Heritage/parser `#२` directly to MW homograph 2.** Preserve the analyzer suffix and candidate boundary; spelling conversion is useful only to find dictionary alternatives. Even `धर्मक्षेत्र` → `Darmakzetra` proves spelling conversion/resolution, not exact lexeme identity. Unresolved correspondence must retain the analysis and let the learner choose alternatives, consistent with ADR 0005.

The artificial `zzzzzzzz` XML lookup returned HTTP 404 with valid endpoint JSON, `status:404`, `xml:[]`, `html:[]`. That is a recognizable endpoint-level lookup miss, unlike an arbitrary 404 HTML page; conservatively report unresolved mapping, not proof that the whole dictionary has no relevant entry. HTTP 403, 429, 500, malformed JSON and network exceptions are technical failures, not dictionary absence. No fallback should occur merely because correspondence is uncertain. [Miss and failure evidence](issue-11-probes/provider-results.json), [ADR 0009](../adr/0009-lazy-dictionary-retrieval-and-fallback.md).

Python observed wildcard `Access-Control-Allow-Origin` on successful native responses. Nevertheless actual Edge returned HTTP 500 with empty bodies for HTML `agni`, XML/HTML `Darmakzetra`, and the legacy `/scans/MWScan/2020/web/webtc/getword.php?key=Darmakzetra&filter=roman&transLit=slp1` route, even with host permission. Raw unpermitted fetches failed CORS. This is an observed client/path discrepancy, **not** proof Cologne is globally down. [Browser results](issue-11-probes/edge-results.json), [dictionary browser results](issue-11-probes/edge-dictionary-results.json).

The guide says there is no rate limiting, but the HTTP probe subsequently received **429 Too Many Requests** for XML, legacy and robots paths. Numeric quota, cause, cooldown and whether shared egress contributed are unknown; no load test or retry bypass was attempted. Stop automatic retries on throttling, surface the technical failure, and use an explicit retry/backoff policy. A production request budget and service-use assurance remain unresolved. [429 observations](issue-11-probes/provider-results.json).

## Display, attribution and terms

Preserve original selection, provider echoes, original lemma spelling, provider identity and any suffix separately from display forms. Heritage can render IAST/Devanāgarī, while parser output principally supplies Devanāgarī. A local, pinned Sanskrit transliteration library is a concrete way to derive an IAST display and SLP1 dictionary query from a known Devanāgarī lemma; identity suffixes must stay outside that conversion. Conversion of analyzer lemmas is permitted by ADR 0003; conversion of selected text to make Heritage eligible is not. The [conversion probe](issue-11-probes/transliteration_probe.cjs) and [results](issue-11-probes/transliteration-results.json) used Node 24.18.1 and pinned `@indic-transliteration/sanscript` 1.3.3. Nine fixtures round-tripped, including `धर्मक्षेत्र` ↔ `Darmakzetra` ↔ `dharmakṣetra`, distinct `सेन`/`सेना` (`sena`/`senA`), `मा` (`mA`/`mā`), and the four first-path constituents. The local library also handled decomposed IAST that the hosted analyzer mishandled. This verifies those display/lemma conversions in Node, not Edge rendering or universal character coverage. Controlled provider/homograph identity fields were retained separately. The [library source and API](https://github.com/indic-transliteration/sanscript.js) are MIT licensed; dependency metadata is retained with the probe.

CDSL's [canonical source-data license](https://github.com/sanskrit-lexicon/csl-orig/blob/master/LICENSE) is **CC BY-SA 4.0**, separate from PHP software licensing. Identify “Monier-Williams Sanskrit-English Dictionary (1899), Cologne Digital Sanskrit Dictionaries,” link the [provider](https://www.sanskrit-lexicon.uni-koeln.de/), retain notices/license link, and indicate transformations. The license imposes attribution/ShareAlike conditions when licensed material or adaptations are shared; it is not evidence of an unlimited hosted-service request allowance. No separate hosted-response caching retention policy was established. Maintain the repository's session-only reading-results policy; do not infer redistribution permission for every unrelated Cologne artifact from this one repository license.

Heritage's [linguistic resources page](https://sanskrit.inria.fr/xml.html) identifies Gérard Huet and **Lesser General Public Licence for Linguistic Resources (LGPLLR)** for its linguistic banks, linking [the actual terms](https://sanskrit.inria.fr/DATA/XML/LGPLLR.pdf). That is not ordinary LGPL, not a license for every dictionary article, and not an authorization to bypass service protections. Attribution should retain Gérard Huet/Sanskrit Heritage, source lemma links and resource version. Exact hosted-output caching/redistribution conditions and acceptable extension use remain unestablished; no blanket grant is asserted.

`sanskrit_parser` [code license](https://github.com/kmadathil/sanskrit_parser/blob/master/LICENSE) is MIT, copyright Karthikeyan Madathil; its [README](https://github.com/kmadathil/sanskrit_parser) identifies Heritage/forms and sanskrit_data layers. The MIT code license does not settle incorporated morphological-data rights. No complete versioned dataset-license inventory, hosted-service terms, caching conditions or operator request quota was established. Preserve parser attribution and source links, and resolve those data/service questions before declaring a production pairing. `/robots.txt` returned 404, which supplies no affirmative use license.

## Follow-up gates

1. Establish a hosted analyzer contract accepting the agreed native Devanāgarī selections, including punctuation/normalization policy and explicit capped/partial-result handling. Parser has positive operational evidence; Heritage would need provider-supported native input plus permitted automated access, not an extension-side workaround.
2. Resolve Cologne's Edge failures and request budget without circumventing protections. Validate complete article boundaries, homographs, inherited entries, identity-based retrieval and safe extraction on the actual browser path.
3. Preserve candidate namespaces and original forms; validate full English grammatical-label mapping and display/lemma transliteration including suffixes and uncommon characters.
4. Establish exact applicable data/service terms and attribution for the chosen deployed versions. Then implement and verify passage choice → constituent analysis → dictionary alternatives → complete article as one Edge workflow.

These are Sanskrit readiness gates. No research finding here blocks Latin delivery, changes an ADR, or authorizes silent scope reduction.
