# Sanskrit analyzer input and passage contract

Research date: **2026-10-05 UTC**. Investigates [#18](https://github.com/YoukouTenhouin/Tensho/issues/18), following [#11](https://github.com/YoukouTenhouin/Tensho/issues/11). This is a research contract, not a production adapter or release acceptance. Preserve [ADR 0001](../adr/0001-separate-analysis-and-dictionary-roles.md), [0002](../adr/0002-explanation-preferences-and-provider-eligibility.md), [0003](../adr/0003-sanskrit-input-capabilities-and-display-transliteration.md), [0004](../adr/0004-explicit-sanskrit-passage-segmentation.md) and [0005](../adr/0005-preserve-uncertainty-in-dictionary-mapping.md), and the [#9 specification](https://github.com/YoukouTenhouin/Tensho/issues/9) / [#13 delivery boundaries](https://github.com/YoukouTenhouin/Tensho/issues/13).

## Decision

**Retain hosted `sanskrit_parser` as the analyzer candidate. The investigation improves its contract but does not pass overall Sanskrit readiness.** Thirteen bounded accountless requests succeeded, including explicit passage segmentation and analysis of a returned constituent. A newly tested native option, `/splits/{passage}?strict=false`, handles the recorded danda-bearing Devanāgarī passage without extension-side rewriting. It invokes substantial provider normalization, not just punctuation removal. Raw decomposed IAST remains unsupported by the sampled operation; ten paths remain potentially capped. Hosted-service terms, quota, deployed-source identity, broad native-input coverage and complete Edge passage-to-dictionary acceptance remain unresolved. Latin delivery is independent. [New observations](issue-18-probes/provider-results.json), [pinned REST source][rest], [normalization source][normalization], [#21](https://github.com/YoukouTenhouin/Tensho/issues/21), [#22](https://github.com/YoukouTenhouin/Tensho/issues/22).

No Heritage or Cologne requests were made. Their previous protection/throttling evidence remains authoritative for this investigation, and no self-hosting requirement or selected-text transliteration workaround is proposed. Historical findings are cited at their immutable commit because the current branch does not contain those research files. [Historical report][history].

## Native operations and input eligibility

The candidate origin is `https://sanskrit-parser.appspot.com`; base path is `/sanskrit_parser/v1`. Construct a GET URL with the entire unchanged input encoded as one UTF-8 path component. There is no validated POST body, explicit input-encoding selector, result-pagination parameter or requested result-count parameter. Literal slash/path edge cases are unvalidated and should remain outside initial eligibility. [REST source][rest], [recorded URLs](issue-18-probes/provider-results.json).

| Operation | Native request and response | Contract and evidence |
| --- | --- | --- |
| Individual-form analysis | `GET /tags/{form}` → `{input, devanagari, tags: [[lemma, [label, …]], …]}` | Source always constructs `SanskritObject(..., strict_io=False)`; changing a splits option does not change this tags behavior. All supplied tuples and tag arrays must survive. An empty array is possible. [REST][rest], [string implementation][strings]. |
| Selected-passage segmentation | `GET /splits/{passage}` with optional `?strict=false` → `{input, devanagari, splits: [[constituent, …], …]}` | Default is strict; **only the literal value `false`** selects nonstrict mode. Source limits paths with `find_all_paths(10)`. It supplies constituent strings, not morphology objects, counts, confidence, offsets or a truncation flag. [REST][rest]. |
| Chosen constituent | `GET /tags/{returned-constituent}` | Submit the exact returned constituent, preserving the passage and chosen path/index. Do not change final `स्`/`र्` to visarga for this request. The source deliberately retains these for further processing; the current `पाण्डवास्` request succeeds. [REST][rest], [results](issue-18-probes/provider-results.json). |
| Version | `GET /version/` → `{version: "0.2.6"}` | Runtime-reported package version only. [Result](issue-18-probes/provider-results.json). |
| Other routes | `/presegmented/`, `/parse-presegmented/` exist in source | Not needed for the agreed explicit segmentation → constituent analysis action and not validated here. Do not infer their behavior from tags/splits. [REST][rest]. |

Suggested eligibility is conservative and operation-specific, **before provider ordering**. It is an adapter policy inferred from the evidence, not a newly discovered service promise:

- Plain classical Devanāgarī individual forms and short passages have positive sampled support. Devanāgarī is native input to both operations; the provider's internal conversion does not require an extension converter. Preserve original bytes/code points and the separate provider echo. [Results](issue-18-probes/provider-results.json), [strings][strings].
- NFC IAST has sampled tags/splits support in #11 and fresh splits support here. The provider auto-detects notation; that does not establish every ASCII scheme or every mixed-script string. Retain a bounded declared capability rather than advertising all schemes accepted by the underlying library. [Historical response evidence][old-results], [new results](issue-18-probes/provider-results.json), [strings][strings].
- NFD IAST with combining marks that the service misreads is ineligible until separately resolved. The new `dharmaks` + U+0323 + `etre` splits response is empty with echo `धर्मक्स्̣एत्रे`; the NFC spelling yields ten paths. An empty array here must not be presented as Sanskrit lexical absence. This contract does **not** silently normalize the learner's selection to make it eligible. [NFC/NFD cases](issue-18-probes/provider-results.json).
- For punctuation-bearing Devanāgarī, declare only the specifically tested native nonstrict capability: the entire selected `धर्मक्षेत्रे कुरुक्षेत्रे ।` is sent unchanged with `strict=false`. Display that the provider normalized punctuation; keep the exact `input` and the changed `devanagari` echo. Do not strip punctuation locally, split the selection into requests, or combine multiple responses into an invented whole-passage result. Double danda, internal punctuation, verse numbers, line breaks and other normalization cases still need corpus validation. [Punctuation comparison](issue-18-probes/provider-results.json), [normalization][normalization].
- Reject empty, whitespace-only, punctuation-only and emoji/mixed unsupported content before requests. `hello🙂` produces empty tags rather than an explicit unsupported response, so the provider cannot supply this distinction for us. Source normalization indexes the final character and is unsafe on deletion-to-empty cases; that is source evidence, not a new failure request. Unknown Devanāgarī `झ्झ्झ्झ्झ` is an eligible artificial form with a valid observed no-segmentation response. [Results](issue-18-probes/provider-results.json), [normalization][normalization].

Nonstrict mode also removes zero-width characters, some punctuation and digits; changes colon to visarga encoding; replaces newlines with spaces; and rewrites some final nasal/vowel forms. Tags additionally defaults to final-visarga `s` replacement, while splits explicitly passes `replace_ending_visarga=None`. Some behavior depends on the installed transliteration library. Therefore advertise **provider-normalized analysis**, retain echoes and do not promise character-preserving linguistic processing or punctuation-only normalization. [Normalization][normalization], [strings][strings], [REST][rest].

No numeric maximum supported passage length or hosted request allowance was established in the inspected sources or observations. The longest fresh request is the 27-code-point danda passage (verify using `len` in the retained requests); the successful shorter samples establish samples, not a limit. Preserve #9/#13 input, response and deadline bounds in future implementation, with a separately declared short-passage limit validated before release. Do not run a load/length sweep to invent a quota. [Probe](issue-18-probes/probe.py), [REST][rest], [#21](https://github.com/YoukouTenhouin/Tensho/issues/21).

Counts below are provider-supplied tuple/path counts, not claims of independent linguistic correctness. All rows are from the [2026-10-05 response fixture](issue-18-probes/provider-results.json), except the explicitly historical compound row.

| Case | Observed result | Required handling |
| --- | --- | --- |
| Wikipedia `संस्कृतम्`, tags | 3 tuples for `संस्कृत` | Preserve all nominal readings. |
| Wikisource `मामकाः पाण्डवाश्चैव`, splits | 10 paths; first is `मामकास्`, `पाण्डवास्`, `च`, `एव` | Expose alternatives; first is provider order, not a correct-choice claim. Mark possibly capped. |
| Learner-choice probe `पाण्डवास्`, tags | 5 tuples for `पाण्डव` | Confirms a returned constituent can be analyzed; do not batch all constituents. |
| Finite `उवाच`, tags | 2 tuples for `वच्` | Preserve first- and third-person perfect readings, primary derivation and parasmaipada endings. |
| Ambiguous `सेनयोः`, tags | 12 tuples across `सेना` and `सेन`; echo `सेनयोस्` | Do not merge candidate tuples or overwrite original selection with echo. The ten-path cap is not a ten-tag cap. |
| `मा`, tags | 6 tuples including `मा#२`, `मा`, `अस्मद्` | Preserve suffix and each response-local candidate; no dictionary homograph inference. |
| Unknown `झ्झ्झ्झ्झ`, splits | 0 paths | Supported no-segmentation outcome, not unsupported input or technical failure. |
| `धर्मक्षेत्रे कुरुक्षेत्रे ।`, default splits | 0 paths | Known punctuation limitation, not a valid no-match for the punctuation capability being proposed. |
| Same original, `strict=false` | 10 paths; provider Devanāgarī echo loses danda | Positive native provider preprocessing; retain original selection and visible limitation. |
| NFC `dharmakṣetre`, splits | 10 paths | Supported sample, possibly capped. |
| NFD equivalent, splits | 0 paths and malformed mixed combining-mark echo | Unsupported raw normalization form, not a Sanskrit lexical miss. |
| `hello🙂`, tags | 0 tuples, partially transliterated echo | Unsupported-content control; local eligibility required. |
| Historical `धर्मक्षेत्रे` | 5 analysis tuples; 10 splits including whole form and `धर्म` + `क्षेत्रे` | Retain supplied compound-initial readings and alternative segmentation; no complete compound-interpretation claim. [2026-10-04 results][old-results]. |

The complete operation flow to implement remains: explicit Analyze passage over only the selection → show every returned segmentation alternative → learner chooses a constituent → analyze that returned form → independently resolve dictionary alternatives → learner chooses an entry. This research validates the first network operations and an explicit recorded constituent choice, **not a native UI interaction or the dictionary tail**. No constituent offsets or alignment are supplied, so a constituent must not be represented as an exact original substring when sandhi changes it. [ADR 0004](../adr/0004-explicit-sanskrit-passage-segmentation.md), [REST][rest], [#22](https://github.com/YoukouTenhouin/Tensho/issues/22).

## Lossless adapter and outcome contract

These are proposed adapter invariants derived from the accepted ADRs and observed wire format:

1. Retain operation, exact selection, requested notation, provider ID, endpoint/options, response-local request ID, raw parsed payload, `input` echo and `devanagari` echo. Keep original strings separate from display conversion. Preserve extra supplied fields within the bounded raw payload; do not silently discard an unexpected known-field shape. Validate required structure before rendering. [ADR 0003](../adr/0003-sanskrit-input-capabilities-and-display-transliteration.md), [ADR 0005](../adr/0005-preserve-uncertainty-in-dictionary-mapping.md), [wire fixtures](issue-18-probes/provider-results.json).
2. Each tags tuple gets a response-local index and remains an independent candidate/interpretation record, even if spelling and tags repeat. Stable lemma identity stays unknown. Preserve the complete original label array; source sets imply order can change between requests, so tuple indices are not durable identities. Do not deduplicate, infer confidence, or combine same-spelling candidates into a lexeme. [Tag serialization][rest], [tag mapper][inria], [ADR 0005](../adr/0005-preserve-uncertainty-in-dictionary-mapping.md).
3. Each split retains its response-local path index, constituent order and exact constituent strings. `returnedPathCount >= 10` means **possibly capped**, never exhaustive; under ten still does not prove complete linguistic coverage. Do not request an eleventh path through undocumented parameters. No total count or pagination is supplied. Compound tags stay visible but cannot prove full compound structure. [REST][rest], [README][readme].
4. `unsupported-input` means no eligible provider for the notation/content/mode. `supported-no-match` is a well-formed empty result for eligible input, ending fallback. `usable` includes ambiguous/possibly capped data and ends fallback. `technical-failure` covers transport, HTTP failure, timeout, malformed or incompatible/oversized payload; only technical failures advance eligible-provider fallback. Permission absence and resource limits retain their separate #9/#13 states. Never turn protection HTML or empty malformed JSON into no-match. Current observations include no new live technical failure; failure classification here is the accepted contract, not a falsely claimed failure probe. [ADR 0001](../adr/0001-separate-analysis-and-dictionary-roles.md), [#13](https://github.com/YoukouTenhouin/Tensho/issues/13).
5. Preserve analysis if dictionary lookup fails or correspondence is unresolved. `मा#२` is the literal provider lemma; for a **conversion copy** isolate base `मा` and metadata suffix `#२`, retaining both and the original. The suffix is not an MW number or a verified stable parser lexeme ID. Unrecognized suffix syntax remains visible and blocks unverified handoff conversion rather than being guessed away. Spelling conversion never establishes lexical correspondence. [Historical identity evidence][history], [new suffix fixture](issue-18-probes/provider-results.json), [ADR 0005](../adr/0005-preserve-uncertainty-in-dictionary-mapping.md).

## English labels

The [mapping fixture](issue-18-probes/labels.json) explicitly covers **21 of 21 distinct labels observed in this run**. It includes case, number, gender, numeral/particle/indeclinable, primary derivation, perfect, person, endings and compound-initial nominal form. The [offline checker](issue-18-probes/validate.py) reconstructs every original tuple from retained records, verifies candidate separation, and verifies a synthetic unfamiliar label remains visible with `english: null`. These are research assertions, not installed production parsing. [Validation output](issue-18-probes/validation-results.json).

The pinned INRIA mapping anchors the critical person reversal: `fst` → `उत्तमपुरुषः` (first person), `snd` → `मध्यमपुरुषः` (second), `trd` → `प्रथमपुरुषः` (third). `para`/`atma` identify endings; they are not interchangeable with `kartari`/`karmaRi` voice. The mapping can supply several labels from one source tag, including passive voice plus ātmanepada, or indeclinable verb form plus a suffix. Retain the entire array and show original Sanskrit labels alongside English. [INRIA mapper][inria].

The other source wrapper contributes `त्रिलिङ्गम्` and `उभयपदम्`, and uses SLP1 strings for participial categories. For example, its `('past','pass')` produces `kta` and `karmaRi`; the INRIA mapper declares mixed Sanskrit and Latin-letter output strings under a Devanāgarī encoding. Do not mechanically translate or transliterate arbitrary unfamiliar labels. Full deployed vocabulary coverage remains unresolved: the 21-label corpus does not exercise every tense, derivation, participle, voice or compound category. A future adapter may add validated English labels but must continue to expose unfamiliar original text. [sanskrit_data wrapper][wrapper], [INRIA mapper][inria].

## Display and lemma-handoff conversion

The [conversion probe](issue-18-probes/transliteration.cjs) uses **`@indic-transliteration/sanscript` 1.3.3**, Node **24.18.1**, with the retained [dependency lock](issue-18-probes/transliteration-package-lock.json) pinning `common_maps` 1.0.6 and `toml` 2.3.6 plus npm integrity values. This extends #11's nine fixtures to **26 exact Devanāgarī ↔ IAST and Devanāgarī ↔ SLP1 round trips**, including ऋ/ॠ/ऌ/ॡ, ङ/ञ/ण, श/ष, anusvāra/visarga/candrabindu, avagraha, oṃ, danda/double danda and ऴ. Output conventions such as candrabindu `~` and danda `|` are library conventions, not a guarantee that every dictionary accepts them. [Results](issue-18-probes/transliteration-results.json), [library source](https://github.com/indic-transliteration/sanscript.js), [locked npm distribution](https://registry.npmjs.org/@indic-transliteration/sanscript/-/sanscript-1.3.3.tgz).

**NFD conversion needs explicit NFC normalization of the conversion copy.** The old single fixture did not establish general NFD support: direct NFD `senā` becomes `सेन̄`, whereas NFC of that copy becomes `सेना`. All 26 fixtures pass after NFC. This correction applies only to display and permitted candidate-lemma handoff conversion; it does not change learner-selected-text eligibility or overwrite originals. [Detailed direct-NFD and NFC results](issue-18-probes/transliteration-results.json), [ADR 0003](../adr/0003-sanskrit-input-capabilities-and-display-transliteration.md).

Five uncommon-character controls expose incomplete conversion rather than proving support: `क़` retains the Devanāgarī nukta in roman output, a ZWJ in `क्‍ष` survives, `अ॑` maps to a combining mark in IAST while the accent survives in SLP1, and Vedic signs `ᳵ`/`ᳶ` pass through unchanged. Preserve the provider original and mark conversion unavailable/partial for unvalidated characters; do not send these outputs as verified dictionary notation. A successful round trip alone is insufficient if the supposedly roman output still contains untranslated symbols. [Uncommon-character results](issue-18-probes/transliteration-results.json).

Suffix isolation is essential: whole-string conversion changes `मा#२` into `mā#2`. The fixture instead retains original `मा#२` and suffix `#२` unchanged, derives only base `मा` → `mā` / `mA`, and keeps `stableLemmaId: null`. This tests spelling/metadata preservation, not MW identity or successful retrieval. Rendering in Edge, full article correspondence and dictionary query acceptance remain #19/#22 work. [Conversion assertion and output](issue-18-probes/transliteration-results.json), [#19](https://github.com/YoukouTenhouin/Tensho/issues/19), [#22](https://github.com/YoukouTenhouin/Tensho/issues/22).

## Reproduction

Offline checks make no network requests:

```sh
python3 docs/research/issue-18-probes/probe.py
python3 docs/research/issue-18-probes/validate.py
node docs/research/issue-18-probes/transliteration.cjs /path/to/node_modules/@indic-transliteration/sanscript
```

To recreate the locked conversion environment, copy `transliteration-package-lock.json` to a temporary directory as `package-lock.json`, create `package.json` containing `{"private":true,"dependencies":{"@indic-transliteration/sanscript":"1.3.3"}}`, and run `npm ci --ignore-scripts --no-audit --no-fund` there. Use the resulting absolute package path in the Node command. Keep dependencies outside the production project. The recorded run used the existing #11 temporary installation with matching lock versions. [Lock](issue-18-probes/transliteration-package-lock.json), [probe](issue-18-probes/transliteration.cjs).

`probe.py --live` explicitly performs the bounded parser-only corpus and refuses to overwrite retained evidence. Do not run it as CI or replay it automatically; inspect #21's service restrictions first, retain original evidence, and stop on any failure/protection. Historical protected Heritage/Cologne URLs are evidence links, not instructions to retry. The full current corpus/tuple validation output is [retained here](issue-18-probes/validation-results.json). This investigation changed no production files or ADRs and performed no native input or audio-routing changes. Publishing the research and updating its tracking tickets does not constitute implementation or release acceptance.
